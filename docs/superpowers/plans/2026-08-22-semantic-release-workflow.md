# Semantic Release Workflow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions workflow that automatically cuts a semantic version (git tag + GitHub Release) on every push to `main` that contains releasable Conventional Commits.

**Architecture:** `semantic-release` (JS tool) runs in a GitHub Actions job. It reads commit messages since the last tag, computes the next version via `@semantic-release/commit-analyzer`, builds release notes via `@semantic-release/release-notes-generator`, and publishes a git tag + GitHub Release via `@semantic-release/github`. No npm package is published; `package.json` exists solely to declare the CI tooling's own dependencies.

**Tech Stack:** Node.js (LTS, via `actions/setup-node`), `semantic-release` 25.x, `@semantic-release/commit-analyzer` 13.x, `@semantic-release/release-notes-generator` 14.x, `@semantic-release/github` 12.x, GitHub Actions.

## Global Constraints

- Single repo-wide version (not per-skill) — per spec `docs/superpowers/specs/2026-08-22-semantic-release-design.md`.
- Only git tag + GitHub Release are produced — no npm publish, no `CHANGELOG.md`, no `.skill` asset uploads.
- Trigger: `push` to `main` only.
- Use the existing `GITHUB_TOKEN` — no new secrets.
- `branches: ["main"]` in `.releaserc.json` — matches the repo's actual default branch.

### Task 1: Add semantic-release npm tooling

**Files:**
- Create: `package.json`
- Create: `.releaserc.json`
- Create: `package-lock.json` (generated by `npm install`)
- Modify: `.gitignore`

**Interfaces:**
- Produces: a working `npm ci` install surface and a `.releaserc.json` config that Task 2's workflow invokes via `npx semantic-release`. Task 2 does not need to know the plugin list — it just runs the CLI.

- [ ] **Step 1: Create `package.json`**

```json
{
  "name": "claude-financial-skills",
  "version": "0.0.0",
  "private": true,
  "description": "CI tooling for semantic-release. The repo itself is a collection of Claude skills, not an npm package.",
  "devDependencies": {
    "semantic-release": "^25.0.9",
    "@semantic-release/commit-analyzer": "^13.0.1",
    "@semantic-release/release-notes-generator": "^14.1.1",
    "@semantic-release/github": "^12.0.9"
  }
}
```

- [ ] **Step 2: Create `.releaserc.json`**

```json
{
  "branches": ["main"],
  "plugins": [
    "@semantic-release/commit-analyzer",
    "@semantic-release/release-notes-generator",
    "@semantic-release/github"
  ]
}
```

- [ ] **Step 3: Add `node_modules/` to `.gitignore`**

Current `.gitignore`:

```
dist/
.DS_Store
__pycache__/
*.pyc
```

Append `node_modules/` so the install step in Step 4 doesn't get staged:

```
dist/
.DS_Store
__pycache__/
*.pyc
node_modules/
```

- [ ] **Step 4: Install dependencies and generate the lockfile**

Run: `npm install`
Expected: exits 0, creates `node_modules/` and `package-lock.json`, no `ERESOLVE` or peer-dependency errors.

- [ ] **Step 5: Dry-run semantic-release locally to validate the config**

The repo has no tags yet and we're not on `main`, so override the branch check for this local validation run only (the real workflow always runs on `main`, where this override isn't needed):

Run:
```bash
GH_TOKEN=$(gh auth token) npx semantic-release --dry-run --branches $(git branch --show-current)
```

Expected: output includes lines like `Analysis of X commits complete: release as X.Y.Z` (first run with no prior tags should resolve to `1.0.0`), ends with `The next release version is 1.0.0`, and does **not** report any error creating the release (dry-run mode skips actual tag/release creation — you should see `Skip step "publish" of plugin "@semantic-release/github" in dry-run mode` or similar). If it instead reports `no new version is released` that's also a valid pass as long as there's no plugin/config error — it just means no releasable commits were found since HEAD, which shouldn't happen here but isn't a config bug.

- [ ] **Step 6: Commit**

```bash
git add package.json package-lock.json .releaserc.json .gitignore
git commit -m "feat: add semantic-release npm tooling and config"
```

### Task 2: Add the release GitHub Actions workflow

**Files:**
- Create: `.github/workflows/release.yml`

**Interfaces:**
- Consumes: `npx semantic-release` (from Task 1's `devDependencies`) and `.releaserc.json` (from Task 1) — the workflow just runs the CLI, all release logic lives in the config already committed.

- [ ] **Step 1: Create `.github/workflows/release.yml`**

```yaml
name: Release

on:
  push:
    branches:
      - main

permissions:
  contents: write
  issues: write
  pull-requests: write

concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: lts/*

      - name: Install dependencies
        run: npm ci

      - name: Release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: npx semantic-release
```

- [ ] **Step 2: Validate the YAML is well-formed**

Run: `ruby -ryaml -e "YAML.load_file('.github/workflows/release.yml'); puts 'valid'"`
Expected: prints `valid` with no exception.

- [ ] **Step 3: Verify job-level structure matches GitHub Actions schema expectations**

Run: `ruby -ryaml -e "d = YAML.load_file('.github/workflows/release.yml'); raise 'missing jobs' unless d['jobs']['release']['steps'].size == 4; puts 'structure ok'"`
Expected: prints `structure ok`.

- [ ] **Step 4: Commit**

```bash
git add .github/workflows/release.yml
git commit -m "feat: add semantic-release GitHub Actions workflow"
```

## Post-plan note (not a task — do not automate)

This plan intentionally stops at committing to the current branch. Pushing
this branch, opening a PR, and merging to `main` are left to the user —
merging is what will trigger the first real release (`v1.0.0`), which is a
user-visible, hard-to-reverse action (creates a real tag + GitHub Release
on the real repo).
